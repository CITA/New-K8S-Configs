1. BACK UP SHARED CERTIFICATE FILES
-----------------------------------
  cd /k8s/configs
  BACKUP="TLS-backup-$(date +%Y%m%d-%H%M%S)"
  mkdir -m 700 "$BACKUP"
  cp -a TLS/cita-wildcard.crt TLS/cita-wildcard.key \
        TLS/STAR_cita_utoronto_ca.ca-bundle "$BACKUP/"
  [ ! -f TLS/fullchain.pem ] || cp -a TLS/fullchain.pem "$BACKUP/"
  chmod 600 "$BACKUP/cita-wildcard.key"
  ls -l "$BACKUP"

Keep the backup securely until all six applications are verified.

2. INSTALL AND CHECK RENEWED CERTIFICATE
----------------------------------------
Copy the renewed files to:
  /k8s/configs/TLS/cita-wildcard.crt
  /k8s/configs/TLS/cita-wildcard.key
  /k8s/configs/TLS/STAR_cita_utoronto_ca.ca-bundle

  cd /k8s/configs/TLS
  chmod 600 cita-wildcard.key
  chmod 644 cita-wildcard.crt STAR_cita_utoronto_ca.ca-bundle
  openssl x509 -in cita-wildcard.crt -noout -subject -issuer -dates
  openssl x509 -in cita-wildcard.crt -noout -text | \
    grep -A2 'Subject Alternative Name'

Check that certificate and private key match (hashes must be identical):
  openssl x509 -in cita-wildcard.crt -pubkey -noout | openssl sha256
  openssl pkey -in cita-wildcard.key -pubout | openssl sha256

STOP if the names, dates or key match are incorrect.

3. GENERATE FULLCHAIN.PEM ONCE FOR ALL SIX APPS
------------------------------------------------
The existing script is:
  /k8s/configs/TLS/generate_fullchain.per.sh

First inspect the NEW CA bundle; do not assume its order is unchanged:
  cd /k8s/configs/TLS
  openssl crl2pkcs7 -nocrl -certfile STAR_cita_utoronto_ca.ca-bundle | \
    openssl pkcs7 -print_certs -noout

The 2026 bundle order was:
  1 USERTrust RSA Certification Authority (trusted root)
  2 Sectigo Public Server Authentication Root R46 (cross-signed)
  3 Sectigo Public Server Authentication CA OV R36 (issuing CA)

The existing script creates the served chain in this order:
  cita-wildcard.crt + CA #3 + CA #2
The self-signed USERTrust root is NOT included in fullchain.pem.

ONLY if the renewed bundle has the same ordering, run:
  ./generate_fullchain.per.sh

Expected:
  3
  cita-wildcard.crt: OK

Confirm the generated chain and private key match:
  grep -c 'BEGIN CERTIFICATE' fullchain.pem
  openssl x509 -in fullchain.pem -pubkey -noout | openssl sha256
  openssl pkey -in cita-wildcard.key -pubout | openssl sha256

Expected count: 3; the two hashes must match. STOP if any check fails.
If the issuer or bundle order changes, update the generation script and
validate the new chain before continuing.

4. CITA-WEBMAIL (APACHE)
-----------------------
Namespace: cita-webmail; deployment: cita-webmail; container: web
VIP: 142.1.127.101; HTTPS name: webmail.cita.utoronto.ca
Config directory: /k8s/configs/cita-webmail
Secret: apache2-certs-keys

Apache configuration (already installed; do not change for renewal):
  SSLCertificateFile /etc/apache2/ssl/cita-wildcard.crt
  SSLCertificateKeyFile /etc/apache2/ssl/cita-wildcard.key

/k8s/configs/cita-webmail/apache-certs-keys.sh must create these Secret keys:
  --from-file=cita-wildcard.crt="$TLS_DIR/fullchain.pem"
  --from-file=cita-wildcard.key="$TLS_DIR/cita-wildcard.key"
  --from-file=STAR_cita_utoronto_ca.ca-bundle="$TLS_DIR/STAR_cita_utoronto_ca.ca-bundle"

Keep the CA bundle key: Roundcube mounts it for IMAP/SMTP verification.

Back up Secret and update:
  cd /k8s/configs/cita-webmail
  kubectl -n cita-webmail get secret apache2-certs-keys -o yaml \
    > /root/apache2-certs-keys-webmail-backup.yaml
  chmod 600 /root/apache2-certs-keys-webmail-backup.yaml
  ./apache-certs-keys.sh

Wait until the mounted file contains 3 certificates:
  kubectl -n cita-webmail exec deploy/cita-webmail -c web -- \
    grep -c 'BEGIN CERTIFICATE' /etc/apache2/ssl/cita-wildcard.crt

Then test and gracefully reload Apache (do NOT restart the DB pod):
  kubectl -n cita-webmail exec deploy/cita-webmail -c web -- apache2ctl configtest
  kubectl -n cita-webmail exec deploy/cita-webmail -c web -- apache2ctl graceful

Verify against the new-cluster VIP (not whatever public DNS resolves to):
  echo | openssl s_client -connect 142.1.127.101:443 \
    -servername webmail.cita.utoronto.ca -showcerts 2>/dev/null | \
    grep -c 'BEGIN CERTIFICATE'
  echo | openssl s_client -connect 142.1.127.101:443 \
    -servername webmail.cita.utoronto.ca \
    -verify_hostname webmail.cita.utoronto.ca 2>&1 | \
    grep 'Verify return code'
  curl -I --resolve webmail.cita.utoronto.ca:443:142.1.127.101 \
    https://webmail.cita.utoronto.ca/

Expected: 3 certificates, Verify return code: 0 (ok), HTTP response.

11. ROLLBACK
------------
If renewal fails, restore the affected application's previous Secret from
its protected backup, for example:

  kubectl apply -f /root/apache2-certs-keys-webmail-backup.yaml

Then wait for the mounted Secret to refresh, test Apache/Nginx configuration,
and gracefully reload the web server. If a ConfigMap was changed, restore
that ConfigMap separately. For Website, a changed Apache ConfigMap mounted
with subPath requires restarting only the Website deployment. Verify the
served certificate, HTTPS and application health. Keep the shared TLS
backup for subsequent correction.

12. NOTES
---------
- Generate fullchain.pem once per renewal; reuse it across all six apps.
- Webmail, Wiki and Indico store fullchain.pem CONTENT under the existing
  Secret key cita-wildcard.crt; their SSL configuration does not change.
- Forms and PDF use the Secret key fullchain.pem and the corresponding
  Nginx ssl_certificate path.
- Website stores fullchain.pem CONTENT as tls.crt, keeps tls.key and
  ca-bundle.crt, and no longer uses SSLCertificateChainFile.
- Webmail and Wiki retain STAR_cita_utoronto_ca.ca-bundle in their Secrets;
  Webmail Roundcube uses it for outbound IMAP/SMTP trust verification.
- Mounted Secret files update asynchronously; wait for 3 certificates before
  reloading the web server. A graceful reload normally avoids pod restart.
- ConfigMaps need not be re-applied if their SSL paths are unchanged.
- Website's old secret-tls.yaml must not be reapplied; its Secret is now
  managed by apache-certs-keys.sh, outside Kustomize resources.
- Do not use curl -k to prove certificate trust; -k disables verification.
- VIP + SNI checks distinguish the new cluster from old public DNS targets.
- This runbook excludes the OLD production PDF deployment (pdf-ns on vm4).
